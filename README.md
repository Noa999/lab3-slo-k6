### Сценарио 3 — Availability (сервер эвдрэл)

| Хэсэг | Тайлбар |
|---|---|
| Тойм | Сервер гэнэт унасан үед систем хэр хурдан сэргэж, хэрэглэгчийн үйлдлийг хэр хадгалж чадах вэ |
| Системийн төлөв | Сервер ажиллаж байгаад гэнэт зогсоод дахин асна (chaos симуляц) |

| Гадаад өдөөлт | Сервер эвдрэл (crash) — ажиллагсан процесс гэнэт зогсоно |
| Шаардлагатай хариу | Систем 10 секундийн дотор дахин асаж, хүсэлт хүлээж авах чадвартай болно |
| Хэмжүүр | Availability ≥ 90% (2 минутын цонхонд, 10с зогсолт орсон), сэргэх хугацаа ≤ 10с |

## 2. SLO хүснэгт

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | /cart/add latency p95 | < 200мс | 20 VU тогтмол ачаалалд, 1 мин |
| Reliability | /pay error rate | < 8% | 1 мин, 20 VU |
| Availability | бүх хүсэлтийн амжилтын хувь | ≥ 90% | 2 мин, 10с зогсолт орсон |

**Босго сонголтын үндэслэл:**
- Performance: /cart/add энгийн, DB хандалтгүй тул хурдан (localhost дээр 1-5мс орчим) хариулах ёстой — 200мс нь маш их сул зай авсан ч мониторинг зорилгоор ашигтай.
- Reliability: серверийн код дотор 5% алдаа хатуу кодлогдсон тул 8% гэдэг нь бодит нөхцөлд тохирсон, бага зэргийн зай үлдээсэн босго.
- Availability: 10 секундийн зогсолт 2 минутын (120с) дунд гэдэг нь ~92% цаг-суурьтай availability өгдөг, тэгэхээр 90% нь бодитой боловч бага зэрэг чанга шаардлага тавьсан.

**Error budget тооцоо (цагаар):**
2 минутын цонхонд 90% availability = 120с × 0.10 = **12 секундийн "эвдрэх эрх"**.

## 3. Мини Chaos туршилт (Availability)

Chaos туршилтын үед сервер ~10 секундээр унасан (18:34:46–18:34:55 орчимд
connection refused алдаа гарсан). Үр дүн:

**Availability threshold:**
✗ 'rate>0.90' rate=87.85% — FAIL

**Reliability threshold:**
✗ 'rate<0.08' rate=15.47% — FAIL

**Бодит availability (хүсэлтээр тооцсон):**
checks_succeeded / checks_total = 5008 / 5700 = 87.85%

Error budget-ээ хэтэрсэн: Алхам 3-т цагаар тооцсон 12 секундийн budget
(2 минутын 10%) байсан бол бодит хэмжилтэд ~12.14% (692/5700) хүсэлт
амжилтгүй болсон — тоо ойролцоо таарч байгаа хэдий ч яг ижил биш. Учир нь
цагаар тооцоход зөвхөн "хугацаа" харгалзсан бол, хүсэлтээр тооцоход сервер
унасан үед хэрэглэгчид үзсэн ЖИНХЭНЭ нөлөө (алдаатай хариу авсан хүсэлтийн
тоо) илүү тодорхой харагдана — учир нь сервер унасан үед хүсэлт шууд алдаа
буцаадаг (connection refused), хэвийн үед бол /report 200-400мс хүлээдэг тул
цаг хугацаагаар тооцох ба хүсэлтээр тооцох хоёрын харьцаа өөр гардаг.

Reliability threshold (http_req_failed{name:pay}) мөн FAIL болсон, учир нь
сервер унасан үед /pay-ийн хүсэлт БҮГД амжилтгүй болдог (серверийн 5%
симуляцилагдсан алдаанаас гадна) — нэг availability эвдрэл хоёр SLO-г зэрэг
зөрчиж байгааг харуулж байна. Эдгээрийг тусгаарлахын тулд Reliability SLI-г
"серверийн 5xx алдааны хувь ЗӨВХӨН сервер AVAILABLE байх үед" гэж
тодотгож болно — өөрөөр хэлбэл availability доройтлыг тусад нь хасаж тооцох.
