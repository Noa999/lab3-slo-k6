# Лаб 3 — Чанарын сценарио → SLO → k6 threshold

## 1. Чанарын сценарио (6 хэсэгтэй формат)

### Сценарио 1 — Performance (/cart/add)

| Хэсэг | Тайлбар |
|---|---|
| Тойм | Хэрэглэгч сагсанд бараа нэмэхэд систем хурдан хариу өгөх ёстой |
| Системийн төлөв | Хэвийн ажиллагаа, сервер эрүүл, ачаалал бага-дунд |
| Орчны төлөв | Production-той адилтгасан локал орчин, DB simulation байхгүй |
| Гадаад өдөөлт | Хэрэглэгч "Сагсанд нэмэх" товч дарна (POST /cart/add) |
| Шаардлагатай хариу | Систем 200 OK хариу буцаана, items тоог шинэчилнэ |
| Хэмжүүр | Латенси p95 < 200мс, 20 VU тогтмол ачаалалд, 1 минут |

### Сценарио 2 — Reliability (/pay)

| Хэсэг | Тайлбар |
|---|---|
| Тойм | Төлбөрийн үйлдэл найдвартай гүйцэтгэгдэх ёстой |
| Системийн төлөв | Хэвийн ажиллагаа, гэхдээ backend-д зарим бүтэлгүйтэл (5% симуляц) байдаг |
| Орчны төлөв | Локал орчин, gateway-ийн бүтэлгүйтлийг санамсаргүйгээр симуляцлав |
| Гадаад өдөөлт | Хэрэглэгч төлбөр хийхийг оролдоно (POST /pay) |
| Шаардлагатай хариу | Ихэнх хүсэлт амжилттай (200), зарим нь 500 алдаатай эргэж болно гэхдээ давтамж бага байх ёстой |
| Хэмжүүр | Error rate (POFOD) < 8%, 20 VU, 1 минут |

### Сценарио 3 — Availability (сервер эвдрэл)

| Хэсэг | Тайлбар |
|---|---|
| Тойм | Сервер гэнэт унасан үед систем хэр хурдан сэргэж, хэрэглэгчийн үйлдлийг хэр хадгалж чадах вэ |
| Системийн төлөв | Сервер ажиллаж байгаад гэнэт зогсоод дахин асна (chaos симуляц) |
| Орчны төлөв | Локал орчин, гар аргаар chaos симуляц хийнэ (Ctrl+C, 10с хүлээж, дахин асаана) |
| Гадаад өдөөлт | Сервер эвдрэл (crash) — ажиллагсан процесс гэнэт зогсоно |
| Шаардлагатай хариу | Систем 10 секундийн дотор дахин асаж, хүсэлт хүлээж авах чадвартай болно |
| Хэмжүүр | Availability ≥ 90% (2 минутын цонхонд, 10с зогсолт орсон), сэргэх хугацаа ≤ 10с |

## 2. SLO хүснэгт

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | /cart/add latency p95 | < 2мс | 20 VU тогтмол ачаалалд, 1 мин |
| Reliability | /pay error rate | < 8% | 1 мин, 20 VU |
| Availability | бүх хүсэлтийн амжилтын хувь | ≥ 90% | 2 мин, 10с зогсолт орсон |

**Босго сонголтын үндэслэл:**
- - Performance: /cart/add энгийн, DB хандалтгүй тул бодит хэмжилтэд p95 нь
  0.6-0.8мс орчим гардаг. Анх 200мс гэж тавьсан нь маш сул, ямар ч
  доройтол илрүүлэхгүй босго байсан тул бодит baseline дээр үндэслэн
  2мс болгож чангаллаа.
- Reliability: серверийн код дотор 5% алдаа хатуу кодлогдсон тул 8% гэдэг нь бодит нөхцөлд тохирсон, бага зэргийн зай үлдээсэн босго.
- Availability: 10 секундийн зогсолт 2 минутын (120с) дунд гэдэг нь ~92% цаг-суурьтай availability өгдөг, тэгэхээр 90% нь бодитой боловч бага зэрэг чанга шаардлага тавьсан.

**Error budget тооцоо (цагаар):**
2 минутын цонхонд 90% availability = 120с × 0.10 = **12 секундийн "эвдрэх эрх"**.

## 3. Мини Chaos туршилт (Availability)

Chaos туршилтын үед сервер ~10 секундээр унасан (18:34:46–18:34:55 орчимд
connection refused алдаа гарсан). Үр дүн:

**Availability threshold:**
✗ 'rate>0.90' rate=87.85% — FAIL

**Reliability threshold:**
✗ 'rate<0.08' rate=15.47% — FAIL

**Бодит availability (хүсэлтээр тооцсон):**
checks_succeeded / checks_total = 5008 / 5700 = 87.85%

Error budget-ээ хэтэрсэн: Алхам 3-т цагаар тооцсон 12 секундийн budget
(2 минутын 10%) байсан бол бодит хэмжилтэд ~12.14% (692/5700) хүсэлт
амжилтгүй болсон — тоо ойролцоо таарч байгаа хэдий ч яг ижил биш. Учир нь
цагаар тооцоход зөвхөн "хугацаа" харгалзсан бол, хүсэлтээр тооцоход сервер
унасан үед хэрэглэгчид үзсэн ЖИНХЭНЭ нөлөө (алдаатай хариу авсан хүсэлтийн
тоо) илүү тодорхой харагдана — учир нь сервер унасан үед хүсэлт шууд алдаа
буцаадаг (connection refused), хэвийн үед бол /report 200-400мс хүлээдэг тул
цаг хугацаагаар тооцох ба хүсэлтээр тооцох хоёрын харьцаа өөр гардаг.

Reliability threshold (http_req_failed{name:pay}) мөн FAIL болсон, учир нь
сервер унасан үед /pay-ийн хүсэлт БҮГД амжилтгүй болдог (серверийн 5%
симуляцилагдсан алдаанаас гадна) — нэг availability эвдрэл хоёр SLO-г зэрэг
зөрчиж байгааг харуулж байна. Эдгээрийг тусгаарлахын тулд Reliability SLI-г
"серверийн 5xx алдааны хувь ЗӨВХӨН сервер AVAILABLE байх үед" гэж
тодотгож болно — өөрөөр хэлбэл availability доройтлыг тусад нь хасаж тооцох.

## 4. Threshold-оо зориуд эвдэх (Step 6)

`/report`-ын threshold-ыг `p(95)<450` → `p(95)<100` болгож slo-test-fail.js
файлд хадгаллаа. Сервер `/report`-д 200-400мс хооронд хариулдаг тул
энэ 100мс-ийн шаардлага физикийн хувьд боломжгүй — ямар ч машин дээр
найдвартайгаар FAIL гардаг.

**Гарсан үр дүн:**
✗ 'p(95)<100' p(95)=388.12ms (FAIL)
✓ 'p(95)<200' p(95)=688.65µs (cart, хэвээрээ PASS)
✓ 'rate<0.08' rate=4.42% (pay, PASS)
✓ 'rate>0.90' rate=98.52% (checks, PASS)



k6 нь `level=error msg="thresholds on metrics 'http_req_duration{name:report}'
have been crossed"` гэсэн алдаатай дуусаж, **exit code = 99** буцаасан
(results/fail.txt файлд бүрэн харагдана). CI/CD pipeline дээр яг ийм
зарчмаар exit code 0-ээс өөр гарвал build/deploy зогсдог — энэ бол
"quality gate" хэрхэн ажилладгийн жинхэнэ жишээ.

Харин `/cart/add`-ын threshold-ыг `p(95)<50` болгосон бол PASS хэвээр
үлдэх байсан, учир нь `/cart/add` бараг тэр даруй (submillisecond) хариулдаг
тул 50мс шаардлага амархан хангагддаг. Энэ нь threshold-ыг санамсаргүй
биш, харин системийн бодит физик хязгаарт үндэслэж сонгох ёстойг харуулж
байна.

## 5. Дүгнэлт

Энэ лабораторид сценарио бичихээс эхлээд бодит k6 threshold хүртэл шилжих
явцад хамгийн хэцүү зүйл нь SLO-гийн босгыг санамсаргүй тоо биш, харин
системийн бодит хэмжилтэд үндэслэж сонгох явдал байлаа. Анх /cart/add-д
200мс гэж тавьсан SLO бодит хэмжилт (p95 ≈ 0.6-0.8мс) дээр ямар ч ач
холбогдолгүй сул босго болсныг олж мэдээд, baseline дээр үндэслэн p(95)<2мс
болгож чангаллаа — энэ засвар нь SLO-г "PASS болгохын тулд" биш, харин
системийн бодит зан төлөвт тохируулах ёстойг практикт харуулсан хэсэг байлаа.
Chaos туршилт availability сценариогийн үнэн зөвийг баталгаажуулсан —
цагаар тооцсон 12 секундийн error budget, хүсэлтээр тооцсон бодит алдааны
хувь (~12%) хоёр ойролцоо боловч яг ижил биш гарсан нь SLI-гээ хэрхэн
сонгохоос хамааран тайлан өөр өөр дүр зураг харуулж болохыг харуулсан чухал
ажиглалт байлаа. Мөн нэг эвдрэл (сервер унах) хэд хэдэн SLO-г зэрэг зөрчиж
болохыг (availability, reliability хоёуланг) харсан нь бодит системд
SLI-гээ анхааралтай тусгаарлаж тодорхойлох хэрэгтэйг сануулав. Threshold-оо
санаатайгаар FAIL болгосон туршилт нь CI/CD-ийн quality gate механизмыг
(exit code 99-оор дамжуулан) тодорхой харуулсан. Мөн анх ажиллуулахдаа
chaos-ын duration ('2m') үндсэн pass-тестдээ санамсаргүй үлдсэнийг олж
харж, зөв '1m' болгож засах шаардлагатай болсон нь тестийн скриптүүдээ
тус тусад нь, зориулалтын дагуу цэвэр хадгалах нь хэр чухал болохыг
сануулсан. Ерөнхийдөө сценарио → SLO → threshold гурван шатны шилжилт нь
чанарын шаардлагыг тодорхойгүй байдлаас автоматаар шалгагддаг код руу
шилжүүлэх үнэ цэнэтэй арга зам болохыг ойлголоо. Хамгийн чухал сургамж
бол: SLO-г тавихаасаа өмнө системээ хэмжиж үзэх ёстой, эс тэгвээс
threshold маш амархан утгагүй болж хувирдаг гэдгийг энэ лаб тодорхой
харуулж чадсан.
